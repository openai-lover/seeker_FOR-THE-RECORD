# Competition review: evidence before polish

Baseline review of the **0.3.0 presentation and 180-second demo**, before the 0.3.1 revision, against the four CLOCK IN judging categories on 20 September 2026. The portal assigns equal weight to stickiness/product-market fit, user experience, innovation, and presentation/demo. The [official announcement](https://solanamobile.com/blog/clock-in-the-solana-mobile-hackathon) explains these categories; the [portal](https://solanamobile.radiant.nexus/) provides the event detail.

The current build is a credible development preview. The available evidence does not support a prediction that it will win. Competing submissions, judge preferences, user retention and the complete live-wallet journey are unknown. A numerical winning probability would be invented.

## What the current evidence supports

| Category | Strength | Main weakness | Highest-value improvement |
|---|---|---|---|
| Stickiness / product-market fit | The saved next action creates a plausible reason to return. Offline usefulness removes an account barrier. | No observed user research, repeat-use cohort or retention result. “Work and wallet decisions” is a broad audience. | Show one person's concrete next visit. Then observe target Seeker users performing that task and report what actually happens. |
| User experience | Complete local workflow, native Android integration, eight languages, large-text checks and explicit local data behavior. | Automated layout checks do not establish human ease of use. The current video makes the phone small and hides much of the interaction behind still images. | Record the main task at a readable scale, including save, return and recovery. Complete physical-device accessibility and fluent-speaker review. |
| Innovation | Attaching private reasoning to immutable activity can give a transaction useful personal context. | A work timer and journal are familiar. The current demo never shows a supported event becoming a saved reflection, so the Solana-specific benefit remains mostly a claim. | Demonstrate event → reason/plan → saved reflection → later return. Mark synthetic data continuously when live data is unavailable. Verify the real-wallet path separately. |
| Presentation / demo | Consistent brand, English copy, clean layout, honest limitations and required file formats. | Only 32 of 180 seconds show moving app interaction. Real taps begin at 0:27. Settings/languages receive 40 seconds. Repeated left-copy/right-phone layouts and a roadmap ending weaken the story. | Reach the app by 0:08; show a complete decision loop; use short captions, detail crops and a memorable brand callback. Keep the evidence disclosure concise and visible. |

The current phone frame is 432 pixels wide in a 1920-pixel landscape video. Longer interface text becomes hard to read when the video is embedded. The revised edit should use larger detail crops around the actual input and saved result, while preserving enough full-screen context to understand navigation.

The activity parser also accepts a deliberately narrow subset of Jupiter v6 classic SPL swaps. A connected judge's wallet may have no supported event to journal. Verify coverage against actual existing history, explain unsupported states clearly and avoid describing this as complete wallet-history support. A separate manual-reflection fallback would be a product option to evaluate; it is not claimed as an implemented feature here.

## Submission priorities

1. Establish meaningful live Solana use on a physical Android device: native wallet selection, an already-existing supported finalized event, a private reflection and a successful reopen. Editing cannot substitute for that evidence.
2. Show the distinctive reflection loop. A labeled fixture is useful for demonstrating implemented UI, while the live-network requirement remains open.
3. Make the first-use and return paths feel effortless. Fewer competing headlines, one obvious next action and readable touch controls matter more than extra decoration.
4. Validate the reason to return with actual target users. Report observations honestly, including confusion and failed tasks.
5. Make source/history and all four required artifacts accessible to judges, then complete the owner-controlled registration and eligibility steps.

## Revised creative direction

Use a short original motion identity: bold editorial type, ink and white, vivid teal actions, one coral record dot, and the existing F mark. The dot acts as punctuation before joining the brand mark. Let actual taps and saved text drive the edit. A few close views should make the product legible without turning the demo into a deck.

The relevant inspiration from polished consumer apps is hierarchy, spacing, copy and responsiveness. Keep the FOR THE RECORD identity original. Do not imply that another company's assets, design system or endorsement are included. Envato material must be identified and licensed before use.

Retain an explicit evidence line in the final video: Android emulator capture; any sample activity is labeled; real-wallet physical-device validation remains pending. Close with the user's saved next action and the exact brand line, so the viewer remembers the product's purpose as well as its current limits.

## What the 0.3.1 revision changes

The final three-minute edit now contains **123 seconds of actual recorded app footage**, with first interaction at **0:08**. A saved next action returns as the next intention. A visibly labeled sample event passes through the actual guided reflection flow, saves locally, reopens and receives a later review. Detail crops make the user's saved words legible. A separate manual 0.3.1 release-app recording shows genuine MWA approval through the official Solana mock wallet on an Android emulator and an empty mainnet history response. No live transaction is fabricated.

The pitch now shows the saved bookmark and reopened sample reflection, rather than relying on a feature list. The identity is an original vector F and coral dot with a short kinetic typography introduction. The GitHub intro is optimized to under 500 KB. There are no stock templates or external music assets.

These changes materially improve the demonstration and make implemented behavior easier to judge. They do not establish product-market fit or complete the missing live event-to-reflection evidence. The largest remaining competitive risks are still the broad target audience, narrow parser coverage, no observed repeat-use data and no physical Seeker/Seed Vault verification. A strong final entry needs those observations more than another cosmetic pass. A numerical winning chance would still be unsupported.
